Modularity and Granularity Best Practices
Separate Routers:

Organize your endpoints into distinct FastAPI APIRouter instances. Each module (Users, Schools, Students, Attendance, Timetable, Admissions, etc.) should have its own router.
This keeps your code clean and manageable.
Python

# app/main.py
from fastapi import FastAPI
from app.routers import users, schools, students, timetable, admissions, # ... and so on

app = FastAPI()

app.include_router(users.router)
app.include_router(users.role_router) # For roles and permissions
app.include_router(users.permission_router)
app.include_router(schools.router)
app.include_router(students.router)
app.include_router(timetable.router)
app.include_router(admissions.router)
# Include all other routers here
Fine-Grained Permissions:

The resource:action pattern (user:read, student:graduate, attendance:take_period) is crucial. Avoid generic permissions like can_manage_users. Instead, break it down to user:create, user:read, user:update, user:delete.
This allows you to create highly specific roles (e.g., a "Class Teacher" role might have attendance:take_period and score:write, but not assessment:create).
Dependency Injection for Reusability:

As shown with has_permission and verify_school_access, FastAPI's dependency injection is your best friend. Create small, reusable functions that encapsulate common logic (authentication, authorization, database sessions).
Pydantic Models for Request/Response:

Define clear Pydantic models for your request bodies (UserCreate, UserUpdate, DepartmentCreate) and response models (UserRead, DepartmentRead). This ensures data integrity, provides validation, and automatically generates OpenAPI documentation.
Multi-Tenancy (School-Specific Data):

Every relevant table (users, roles, departments, classes, students, teachers, assessments, fees, etc.) should have a school_id foreign key.
When a user makes a request, your authorization dependencies should ensure they can only access data belonging to their school_id (unless they have a global "SuperAdmin" role or specific "admin:all_schools" permission).
This is enforced in the verify_school_access dependency and also explicitly within API routes when filtering data.
Admin UI for RBAC Management:

The endpoints for /api/roles, /api/permissions, /api/user_roles, /api/role_permissions will be consumed by your Web Interface (Next.js) for an Admin Panel. This is where administrators can define roles, assign permissions to roles, and assign roles to users without touching the database directly.
Initial Seed Data:

Have a script to seed your database with initial global roles (e.g., 'SuperAdmin'), a default 'Admin' role, and all your predefined permissions (user:read, student:graduate, etc.) when setting up a new environment. This ensures your system starts with a functional RBAC foundation.
By following these principles, you'll build a highly modular backend that is flexible enough to handle the diverse permission needs of different school types and staff roles. Good luck!

### **4. Period Attendance Endpoints (New)**

These endpoints are for recording and managing attendance specifically for each scheduled period.

* **`POST /api/attendance/period/{school_id}`**
    * **Description:** Records period-specific attendance for a group of students in a class, typically taken by a teacher for a scheduled period.
    * **Permissions:** `attendance:period:take`
    * **Request Body:**
        * `date` (date string): The date the attendance is taken.
        * `academic_session_id` (integer): ID of the academic session.
        * `term_id` (integer): ID of the term.
        * `class_id` (integer): ID of the class for which attendance is being taken.
        * `subject_id` (integer): ID of the subject being taught during this period.
        * `teacher_id` (integer): ID of the teacher taking attendance.
        * `period_id` (integer): ID of the specific period (e.g., Period 1).
        * `verified_location_id` (integer): ID of the authenticated location where attendance was taken (from `/api/attendance/verify-location`).
        * `students_attendance` (array of objects):
            * `student_id` (integer)
            * `status` (string): e.g., "PRESENT", "ABSENT", "LATE", "EXCUSED"
            * `notes` (string, optional): Any specific notes for this student's attendance.
    * **Success Response:** Confirmation of attendance record creation, potentially with a summary.

* **`PUT /api/attendance/period/{school_id}/{attendance_record_id}`**
    * **Description:** Updates a specific period attendance record for a student.
    * **Permissions:** `attendance:period:update`
    * **Request Body:** (Partial update allowed)
        * `status` (string, optional): New attendance status.
        * `notes` (string, optional): Updated notes.
        * `verified_location_id` (integer, optional): If re-verifying location.
    * **Success Response:** Updated attendance record details.

* **`GET /api/attendance/period/{school_id}`**
    * **Description:** Retrieves period attendance records for a specific school, with various filtering options.
    * **Permissions:** `attendance:period:read`
    * **Query Parameters (all optional):**
        * `start_date` (date string)
        * `end_date` (date string)
        * `academic_session_id` (integer)
        * `term_id` (integer)
        * `class_id` (integer)
        * `subject_id` (integer)
        * `teacher_id` (integer)
        * `student_id` (integer)
        * `period_id` (integer)
        * `status` (string): Filter by attendance status (e.g., "ABSENT").
    * **Success Response:** A list of period attendance records, including student, class, subject, teacher, and period details.

* **`GET /api/attendance/period/{school_id}/student/{student_id}/statistics`**
    * **Description:** Provides period attendance statistics for a specific student (e.g., total periods, present count, absent count, late count, excused count).
    * **Permissions:** `attendance:period:read_statistics`
    * **Query Parameters (all optional):**
        * `start_date` (date string)
        * `end_date` (date string)
        * `academic_session_id` (integer)
        * `term_id` (integer)
        * `subject_id` (integer)
    * **Success Response:** An object with attendance statistics for the student.

* **`GET /api/attendance/period/{school_id}/class/{class_id}/subject/{subject_id}/statistics`**
    * **Description:** Provides period attendance statistics for a specific class and subject combination (e.g., summary of attendance for all students in that class for that subject).
    * **Permissions:** `attendance:period:read_statistics`
    * **Query Parameters (all optional):**
        * `start_date` (date string)
        * `end_date` (date string)
        * `academic_session_id` (integer)
        * `term_id` (integer)
        * `period_id` (integer)
    * **Success Response:** An object with aggregated attendance statistics for the class/subject, possibly broken down by student or status.

* **`GET /api/attendance/period/{school_id}/teacher/{teacher_id}/statistics`**
    * **Description:** Provides attendance statistics for periods taught by a specific teacher.
    * **Permissions:** `attendance:period:read_statistics`
    * **Query Parameters (all optional):**
        * `start_date` (date string)
        * `end_date` (date string)
        * `academic_session_id` (integer)
        * `term_id` (integer)
    * **Success Response:** An object with aggregated attendance statistics for the teacher's periods.


Endpoint Categories:

1. Report Generation Endpoints
These endpoints are responsible for triggering the creation and delivery of reports based on requested data, format, and design.

GET /api/reports/student/{student_id}/generate
Description: Generates a comprehensive report (e.g., report card, results summary) for a specific student. The report's format (PDF, CSV, XLSX) and visual design will be determined by query parameters. It will leverage pre-designed or custom templates and incorporate school branding.
GET /api/reports/class/{class_id}/generate
Description: Generates a report (e.g., class performance summary, attendance report) for an entire class. Similar to the student report, format and design are specified via query parameters, using available templates and school branding.
2. Report Template Management Endpoints
These endpoints allow school administrators to manage the report templates available for their school. This includes system-provided pre-designed templates and custom templates uploaded by the school, enabling dynamic selection and customization from the web-based report card builder.

POST /api/report-templates/{school_id}
Description: Uploads a new custom report template (which could be an HTML file for PDF generation, or a configuration for other formats) for a specific school. This enables the school to extend the available designs beyond the pre-designed options.
GET /api/report-templates/{school_id}
Description: Retrieves a list of all available report templates for a specific school. This list includes both the system's pre-designed templates and any custom templates uploaded by the school, providing options for the report card builder.
GET /api/report-templates/{school_id}/{template_id}
Description: Retrieves the content and detailed metadata of a specific report template, identified by its ID. This is crucial for the web-based report card builder to preview and potentially modify template content.
PUT /api/report-templates/{school_id}/{template_id}
Description: Updates the content or metadata of an existing report template. This allows for modification of custom templates and potentially the activation/deactivation of pre-designed ones.
DELETE /api/report-templates/{school_id}/{template_id}
Description: Deletes a specific custom report template from a school's library. Pre-designed, system-provided templates should not be deletable.
3. School Branding & Customization Endpoints
These endpoints allow administrators to manage school-specific branding elements that will be dynamically incorporated into reports. This ensures all generated documents align with the school's identity.

POST /api/schools/{school_id}/logo
Description: Uploads or updates the official logo image for the school. This logo will then be used in all generated reports that support it.
GET /api/schools/{school_id}/branding
Description: Retrieves school-specific branding information, including the URL to the uploaded logo, primary and secondary color schemes, and slogan.
PUT /api/schools/{school_id}/branding
Description: Updates various school-specific branding details, such as color codes or a slogan, which can be applied to report designs.
